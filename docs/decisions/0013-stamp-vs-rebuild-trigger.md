# 0013: 刻印 (provenance) の対象とリビルドの引き金を別集合として保つ

- **状態**: 採用 (2026-08-15)

- **文脈**: `WatchSession.computeSourceStamp()` は監視ディレクトリ配下の **`*.swift` だけ**を (パス:mtime:サイズ) でハッシュしていた。当時はこれで足りていた — `.metal` を保存しても絵は変わらなかったので、刻印が `.swift` だけを指していても嘘にはならない。

  metaphor#648 / metaphor#669 でシェーダのホットリロードが入り、**`.metal` の保存が再起動なしで絵を変える**ようになって前提が崩れた。CONTRACT.md 契約点 4 の `sourceStamp` は「観測フレームがどのソース版を反映するか」の provenance なので、シェーダソースだけが違う 2 つの実行が同じ刻印を名乗るのは**刻印が嘘をついている**状態にあたる。

  素直に対象を広げると、次の衝突に当たる。`.swift` の集合はもう 1 つの役割 — **再ビルドの引き金** (`swiftSourceSignature`) — も兼ねていた。両者が同じ集合だったので今まで区別する必要が無かったが、`.metal` を引き金にも足すと**保存のたびに再ビルド + 再起動が走り、metaphor 側のホットリロードがただの再起動に化けて価値が消える**。

- **決定**: 「刻印の対象」と「リビルドの引き金」を**意図的に別集合**として保つ。

  - 刻印 (`stampedSourceExtensions`) は `["swift", "metal"]` に広げる
  - リビルドの引き金 (`swiftSourceSignature`) は `.swift` のまま据え置く
  - `latestSwiftModification()` も変更しない (これはリビルドの検知遅延の見積もりであり、リビルドを起こすのは `.swift` だけ)
  - 分離の意図は `WatchSession.swift` と `FileWatching.swift` の**両側にコメントで残す**。今は 2 つの集合がほぼ重なっているので、片方を触る人が「揃っていないのは漏れだ」と読んで統一してしまうのを防ぐ
  - 回帰ガードとして、`.metal` 編集で刻印が変わること / **同じ編集で `swiftSourceSignature` が変わらないこと**の両方をテストで固定する

  CONTRACT.md は変更しない。契約点 4 は `sourceStamp` を「編集ごとに変わる識別子 (例: 監視対象ソースの mtime/サイズ集約ハッシュ)」と opaque に定義しており、cli 内部の算出対象を広げるのは契約の変更にあたらない。

- **影響**: `.swift` 編集で再起動が起きたとき、その刻印が `.swift` と `.metal` 両方の現在版を正しく指すようになった。

  **`.metal` 単独編集の反映は、これでは機械検出できない。** `METAPHOR_SOURCE_STAMP` は子プロセスの起動時にしか注入されず、producer 側も init 時に一度だけ解決するので、対象を広げても効くのは次の再起動から。cli が途中で刻印を差し込む形にすると、ホットリロードのデバウンス (120ms) + MSL コンパイルの窓で「**新しい刻印・古い描画**」の偽陽性が出る。コンパイル失敗時は直前の動くシェーダが残る設計なので、なおさら「刻印が進んだ = 反映された」は成り立たない。

  リロードが着地した瞬間を知っているのは producer だけなので、そちらは metaphor#671 (PR metaphor#674) で `frame.json` にトップレベルキー `shaders` (`generation` / `digest` / `lastError?`) を additive で載せる形に解決した。cli は MCP が `frame.json` を verbatim 透過するのでコード変更が無く、#131 は契約ファイルのバイト等値コピーだけ ([ADR 0004](0004-wire-schema-canon.md))。

  一般化すると、**「変化を記録する対象」と「変化に反応する対象」は別の問いに答えている**。前者は provenance の正しさ、後者はコストと体験のトレードオフで決まる。今後どちらかに拡張子や監視対象を足すときは、もう片方に足すかを独立に判断する。
