# 0006: 変更検知は FSEvents を主、低頻度ポーリングを安全網にする

- **状態**: 採用 (2026-08-01)

- **文脈**: `metaphor watch` の変更検知は 0.4 秒間隔のポーリングだった。#88 (編集 → 反映の往復を速くする) の分解計測 (#89) で、検知だけで **p50 154ms / max 210ms** を使っていることが分かった — ポーリング間隔の期待値そのもので、間隔を詰める以外に縮めようがない。

  間隔を詰めれば CPU を常時食う。クリエイティブコーディングの主戦場は「保存して即座に絵が変わる」体験なので、この遅延はそのまま体験の質になる。

  一方、FSEvents へ全面移行するのも一択ではない。**ネットワークマウント等のボリュームでは FSEvents が届かない**ことがあり、そこで watch が沈黙すると「保存しても何も起きない」という最悪の壊れ方をする。

- **決定**: `FSEventsFileWatcher` を新設して watch / viewer / mcp の既定にし (合流 latency 0.1s)、**低頻度 2 秒の安全ポーリングを併走**させる。

  - 発火したかどうかに関わらず、再ビルドの判定は**従来と同じソース署名の照合** (`swiftSourceSignature(in:)` に共通化) で行う。`.build` へのビルド出力などスプリアスなイベントで再ビルドしない。`.build` / `.metaphor` / `.git` はカーネル段階でも除外する
  - 判定が共通なので、FSEvents と安全ポーリングが両方発火しても二重にビルドしない
  - `PollingFileWatcher` はテスト・予備用として残す

- **影響**: 実測で **detect_ms が p50 154.4 → 28.2ms (max 209.5 → 70.4ms)**。

  「イベントは検知の**きっかけ**に過ぎず、ビルドするかどうかはソース署名が決める」という形にしたことで、イベント源を差し替えても振る舞いが変わらない構造になった。FSEvents が届かない環境では 2 秒遅れるだけで、機能は失われない。

  検知系のテストは実ファイルシステムを使った統合テストで、`evaluate()` の通知を一時的に破壊して赤くなることを確認してある (編集検知 / 新規ファイル / `.build` 無視 / 安全網 / 停止の 5 本)。

  なお、この時点では往復全体の律速は検知ではなかった — 未計上の ~1.4s が残り、[ADR 0007](0007-executable-target-fallback.md) がそれを潰した。
