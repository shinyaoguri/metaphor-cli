# 0009: リロードをまたぐ状態の引き継ぎは、中身を解釈せず運ぶだけにする

- **状態**: 採用 (2026-08-10)

- **文脈**: `metaphor watch` のホットリロードは子プロセスを作り直すので、**スケッチが積み上げた状態と時計が毎回ゼロに戻る**。パーティクルが溜まっていく系・時間で育っていく系のスケッチでは、1 行直すたびに最初からやり直しになる。

  状態を運ぶには、子が死ぬ前に吸い上げて次の子へ渡す必要がある。問題は**誰がペイロードの形を知るか**で、cli が中身を型として知ると、スケッチ側で状態の構造を変えるたびに cli の更新が要る — ライブラリと CLI が別リリースで動くこの構成では成立しない。

- **決定**: producer (metaphor) 側に契約点 8 (`.metaphor/state/`) を新設し、**cli は運ぶだけで中身を解釈しない**。

  - `StateHandoff` が `.metaphor/state/save-request.json` へ新しい `id` をアトミックに書き (`.tmp` → rename)、`state.json` の `savedRequestId` が一致するまでポーリングする (既定 250ms タイムアウト・5ms 間隔)
  - ペイロード (`runtime` / `user`) の中身は**読まない**。cli が知るのはファイルのパスと `id` の一致だけ
  - `WatchSession` は子を kill する**前**に保存を要求し、取れた `state.json` のパスを次の起動の `METAPHOR_RESTORE_STATE` へ入れる。子には `METAPHOR_STATE=1` を明示注入する (`--no-viewer` でも運べるように。ユーザーが環境で設定していればそれを尊重)
  - **無応答なら以降は要求しない** — 状態保持を使っていないスケッチで、リロードのたびに 250ms を捨てないためのヒューリスティック (watch セッション単位)
  - 失敗 (書けない・タイムアウト・応答なし) は握りつぶして通常起動する。**状態の引き継ぎは付加価値であって、リロードそのものを止める理由にはならない**

  `id` の往復で一致を確かめるのは、**前回実行が残した古い `state.json` を拾わない**ため。ファイルの存在だけを見ると、死んだ子の遺した状態を新しい子に注ぎ込んでしまう。

- **影響**: 状態を持つスケッチでも、編集 → リロードで文脈が保たれる。cli はペイロードの型を一切知らないので、スケッチ側が状態の構造を変えても cli の更新は要らない。

  代償は 250ms のタイムアウトで、状態保持を実装していない producer に当たると初回だけこれを払う (2 回目以降は要求しない)。

  テストは擬似 producer (`save-request.json` を見て `id` エコー付きで `state.json` を書く小さなスレッド) を相手に cli 側の振る舞いだけを検証する形で、Metal もスケッチ本体も要らない。実装を一時的に壊して赤くなることを 3 点 (`METAPHOR_STATE` 注入 / 無応答後の抑止 / `savedRequestId` の一致判定) で確認済み。
