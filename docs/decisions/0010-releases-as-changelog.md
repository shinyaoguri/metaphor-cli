# 0010: 変更履歴の正本は GitHub Releases に置き、`CHANGELOG.md` は凍結する

- **状態**: 採用 (2026-08-16)

- **文脈**: 個人標準への適合 (#94) で `CHANGELOG.md` を追加したが、**更新の仕組みが無いまま**だった。#97 がその時点で陳腐化を予測し、実際そのとおりになった:

  - 最後のリリース済み版節が `## [0.5.1] - 2026-08-01` で、タグは既に v0.11.0 (v0.6.0 以降 10 版が未記載)
  - `## [Unreleased]` に残っていた 3 項目は**全部出荷済み**だった
  - 実害も出た。metaphor#585 の調査で「`set_param` はリリース版で使えるのか」に CHANGELOG が答えられず、`git tag --contains` を引くはめになった

  原因は怠慢ではなく構造にある。このリポジトリは **PR のマージだけでリリースが走る** ([ADR 0002](0002-release-from-pr-title.md)) ので、人間が「これからリリースする」と意識する瞬間が無く、`Unreleased` → 版節の**昇格工程を挿す場所が無い**。#97 の選択肢 B (PR ごとに追記する規約) は、追記自体は行われていて昇格だけが落ちたことで既に反証されていた。

- **決定**: `CHANGELOG.md` をやめ、**GitHub Releases を変更履歴の唯一の正本**にする (#97 の選択肢 C)。

  選択肢 A (release workflow から自動追記) を採らなかったのは、protected main への書き戻し機構 (App token → PR → auto-merge) を足したうえで、中身が `generate_release_notes` の複製にしかならないため。`CHANGELOG.md` の価値だった「利用者に見える変化だけの要約」という粒度は自動生成では戻らないので、二重管理のコストだけが残る。C なら陳腐化が構造的に起こりえない。

  個人標準の `changelog-exists` は `recommended` で、fix にも「リリース workflow から自動生成してもよい」とある。全版の履歴を持つ Releases でその意図は満たされる。

  - `CHANGELOG.md` は正本へのポインタ + 引き方 (`gh release list` / `gh release view` / compare URL) + やめた理由を置く薄いファイルにする。v0.1.0〜v0.5.1 の手書き要約は `## アーカイブ — v0.5.1 まで` の下にそのまま残す (当時の自動生成ノートより読みやすく、消す理由が無い。見出しから v0.6.0 以降が無いことも自明になる)
  - **`ci.yml` に `Check CHANGELOG stays a pointer` を追加**する。`## [Unreleased]` の復活と、版見出しの集合がアーカイブ (7 個) から増減したときに落ちる

- **影響**: 「CHANGELOG があるのに古い」という、無いより悪い状態が構造的に起こらなくなった。

  CI 検査を足したのは、**文書ルールだけでは親切心で版節を書き戻す人間・エージェントを止められない**から。AGENTS.md が「追記すると CI が落ちる」と書いているのはこの検査を指す。

  具体的なタグを例に書くとそれ自体が古びるので、`CHANGELOG.md` のコマンド例と compare URL はプレースホルダにしてある。
